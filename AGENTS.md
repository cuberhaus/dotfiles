# dotfiles

Personal Linux/Unix dotfiles for Arch, Manjaro, Ubuntu, and macOS — shell, editor, window-manager, and tooling configs. Managed via **GNU Stow**; primary shell is **Zsh** (antigen + p10k) with bash fallbacks.

## Architecture

- Repo lives at `~/cuberhaus/dotfiles/`; `~/cuberhaus` is the stow directory and `dotfiles` is the package. Stow symlinks `.config/`, `.local/`, `.vim/`, `.xmonad/`, `.zshenv`, etc. into `$HOME`.
- `$DOTFILES` (exported by `.zshenv`) resolves the symlink back to the repo root — scripts and configs should reference paths via `$DOTFILES`, not a hardcoded checkout path.
- OS-specific setup is segregated under `.local/scripts/bootstrap/` (one entrypoint per OS, plus shared `base_functions` and per-OS `*_functions` files).
- Volatile, app-rewritten files (Warp prefs, LibreOffice settings, VLC interface config) are tracked but automatically masked with `git update-index --skip-worktree` via `clone-all`, `make install`, and bootstrap.

## Build and Test

`make help` lists everything. Common targets:

- `make install` / `make uninstall` / `make restow` — stow lifecycle (install and restow back up conflicts first via `.local/scripts/stow-backup-conflicts`).
- `make dry-run` — simulate stow, report conflicts and what install/restow would back up, no changes.
- `make lint` (shellcheck), `make test` (unit tests), and `make check` (tests + shellcheck + markdownlint + vint).
- `make audit-installation` — read-only comparison of the checkout, Stow-managed files, active bootstrap package declarations, and native automations. Set `PROFILE=arch|manjaro|ubuntu|ubuntu-windows|mac|work` to override auto-detection. Every `[MISSING]` or `[DRIFT]` finding carries a `Fix:` line with the exact command (the manager's install line, one `snap install … --classic` per snap, `make bootstrap-<profile>` only when nothing narrower exists); a new check must print one, never a bare "run the bootstrap". An apt name with no install candidate gets `sudo apt-get update && …` plus a `#` note, because the plain install would fail.
- `make bootstrap-{arch,manjaro,ubuntu,mac,work}` — full OS provisioning; **read the script first**, it installs hundreds of packages.
- `make bootstrap-gentoo-dry-run` / `make bootstrap-gentoo` — experimental Gentoo profile that has never run on a real machine. Always dry-run first; it is excluded from `make audit-installation` and profile detection on purpose. See `docs/GENTOO-BOOTSTRAP.md`.

## Conventions

- **POSIX-compliant bash** by default; explicitly note when a feature requires Zsh.
- Use robust patterns: `find … -print0 | xargs -0`, `while IFS= read -r -d ''`, prefer `awk`/`sed`/`grep`/`find` over ad-hoc parsing.
- New aliases/functions in `.config/zsh/aliases` and `.config/zsh/functions` must not shadow standard Unix commands unless they intentionally add defaults to that same command.
- User-facing output uses ANSI colors: success `\033[32m`, warning `\033[33m`, info `\033[34m`, always reset with `\033[0m`.
- Parallelize repo/file iteration with `xargs -P`, backgrounded `&` jobs + `wait`, especially for multi-repo helpers like `add_pat`.
- **Vendor apt repositories**: register them only through `apt_vendor_source_ensure` / `ide_apt_sources_ensure` in `base_functions` (deb822 `.sources`, written after the signing key is verified); never hand-write a legacy `.list`. A flat repository (a suite ending in `/`, like NVIDIA's) passes an empty COMPONENTS argument, which leaves out the `Components:` line apt rejects there. An Ubuntu release upgrade disables third-party sources and the weekly `apt-get full-upgrade` then skips their packages silently, which is why `make audit-installation` checks the IDE packages and `make repair REPAIR=ide-repos` fixes them. Agents preview that repair with `DRY_RUN=true` and leave the real run (it uses `sudo`) to the user.

### Shell command catalog

- The interactive `commands` function in `.config/zsh/functions` builds the catalog from annotations in the files themselves; do not maintain a second hardcoded catalog. It groups by purpose, not by kind, and asks the live shell which names exist, so a definition behind a failed `if` (an Arch-only alias on Ubuntu) is not listed. `commands WORD...` filters by name, group, description, or what an alias runs; `-v` adds what each alias runs and where each function and script lives; names that start with `_` are internal helpers, shown only with `-a`; `commands --list` prints one tab-separated line per command (kind, name, group, expansion, source) for scripts and tests.
- Put aliases and small shell wrappers in `.config/zsh/aliases`, reusable functions in `.config/zsh/functions`, and standalone executables in `.local/scripts/bin`. A name defined as more than one kind is listed once, as the one the shell runs (alias, then function, then script), and `-v` says what it hides.
- A `##@ Group name` line starts a group for the aliases and functions below it, up to the next `##@`; each file starts with none. Name groups by purpose (`Git`, `Packages & updates`). Entries with no group are listed last under **Other**, and groups appear in the order they first show up: aliases, then functions, then scripts.
- Add a concise behavioral description immediately above every alias and function using a `##` documentation comment. Plain `#` comments and blank lines may sit between it and the definition; any code line in between drops it. The catalog supports `alias name=`, `name()`, `name ()`, `function name()`, and `function name {`, and a name defined twice (an alias in each branch of an `if`) keeps the first description:

  ```bash
  ##@ Git across repositories

  ## Show git status for every repository below the current directory.
  status() { git-recurse "$@" git status; }
  ```

- An alias without a `##` line is listed as `(no description)`; write the line instead of relying on that. An alias that only renames one command (`gr="git-recurse"`) and has no description is folded into that command's entry as `git-recurse (gr)`, and one that starts with its own name (`grep='grep -i --color=auto'`) also shows the options it adds.
- Start each executable in `.local/scripts/bin` (an executable regular file directly in that folder) with `# Description: ...` and `# Group: ...` comments after the shebang; the catalog uses them as the command's description and group. The header ends at the first line that is neither blank nor a comment.
- Keep descriptions imperative, behavior-focused, and short enough to scan. Do not describe only the implementation location or repeat the command name.
- **Every command answers `-h` and `--help`.** A script or function checks for them first, before any dependency check, argument handling, or action, prints `Usage: NAME ...` and what the command does on stdout, and exits 0 (`return 0` in a function) with nothing on stderr. An alias hands every word you type to its last command, so it is a safe shortcut only when it is one simple command: a chain (`a; b`, `a && b`, a pipe, a trailing `&`) has already run its first part when `-h` arrives, and fixed arguments of one of our scripts (`restore-app-data anki --apply`) come before yours and can swallow it. Make those a function that answers `-h` itself, or a script (`yolo` is a script for that reason). An alias of one of our commands reaches that command's help, an alias of another program leaves `-h` to that program (`ls`, `grep`) except `ssh` and the browsers with a fixed host or address, where what you add lands after it as a remote command or another page (`erag-tunnel` and `erag-chrome` are functions for that reason), and an alias of a git subcommand must leave the repository alone for `-h` (`git commit -m` would take it as the message, so `gc` is a function). A command that acts and has no use for an extra argument refuses it instead of treating it as data: `yolo --dry-run` must not push, and `add_pat` and `clone-all` refuse a word that starts with `-`.
- When an alias becomes a function, put `unalias NAME 2>/dev/null` before the definition. A shell that loaded the old file still has the alias, and a function whose name is a live alias is a parse error that stops the rest of the file. For a function defined inside an `if` block the `unalias` goes before the block, because the shell parses the whole block before it runs any of it (`clean` and `mirror`), and it must not remove an alias that a later block defines (the Arch `mirror`).
- `tests/test_command_help.sh` enforces both rules without a list of its own. It takes every script, function, and alias from `commands --list` in each variant (plain, Ubuntu, Arch, Manjaro, Ubuntu on Windows, macOS) under Bash and Zsh, and runs `NAME -h` and `NAME --help` in a clean `env -i` shell, in a throwaway HOME and working directory, whose PATH holds a few harmless tools and tripwire stand-ins for `git`, `sudo`, `ssh`, `rclone`, `apt` and the like. A command fails when it exits non-zero, writes to stderr, prints no `Usage` line that names it, starts a tripwire, or changes a file, and the message names what it tried to start. It judges aliases as above (git aliases against a scratch repository with real `git`) and sources `aliases` over live aliases of the old names to check each `unalias`. A new command needs no entry: it fails until it answers `-h`.
- Validate catalog changes with `shellcheck .config/zsh/aliases .config/zsh/functions`, then source both files and run `commands` under Bash and Zsh, then run `bash tests/test_commands.sh` and `bash tests/test_command_help.sh`.

## Pitfalls

- **Never overwrite `$HOME` files blindly** — symlink via stow or back up first; `make install` and `make restow` already handle conflict backups.
- **Stow conflicts**: `stow-backup-conflicts` (run by `install`, `restow`, and the bootstrap preflight) moves whatever blocks Stow into `~/.dotfiles-backup/<timestamp>/`: a plain file, or a symlink Stow did not create, which includes an absolute link to the repo's own file (`existing target is not owned by stow`). Keep app-owned live state out of its reach with `.stow-local-ignore`: `~/.config/dconf/user` is the live GNOME database (dconf overwrites a symlink and gnome-shell keeps the file mapped), so `^/\.config/dconf(/|$)` must stay or the next `install` moves the desktop settings aside for a stale 2023 snapshot of two Eye of GNOME settings. `tests/test_stow_conflicts.sh` covers it with the real Stow.
- **Do not run `sudo apt install`, `pacman -S`, `brew install`, `emerge`, or edit `/etc/`** without asking the user. Bootstrap scripts are opt-in.
- Keep platform-specific config separate (WSL vs native Linux vs macOS); don't merge Arch and Ubuntu package lists.
- Destructive helpers must support a dry-run mode and print clear usage.
- **Bash prompt**: the colored prompt in `.bashrc` assigns `PS1` once and only refreshes the variables it references from `PROMPT_COMMAND`, because VS Code/Cursor shell integration wraps `PS1` and re-wraps it whenever it changes. Do not re-add prompt plugins that rebuild `PS1` on every prompt (the removed `bash-git-prompt` did). It honors `NO_COLOR`, skips `TERM=dumb`, and `PROMPT_GIT=0` hides the git segment. Chat-tool terminals run `bash --noprofile --norc` on purpose and stay plain. `tests/test_bashrc_prompt.sh` covers it.
- **ROG brightness**: on the G635LX in dGPU/MUX mode `nvidia_wmi_ec_backlight` is a ghost device (values are accepted, the panel ignores them), so brightness tools writing to it appear to do nothing. The fix is `acpi_backlight=native` from `.local/scripts/brightness_fix.sh`; keep it after `shutdown_fix` in the `work` bootstrap and read `docs/ROG-BRIGHTNESS-DIAGNOSIS.md` before changing it.
- **asusctl**: `.local/scripts/asusctl_install.sh` builds a pinned release and gates itself on the hardware (ASUS vendor, a family `asusd` supports, kernel 6.19+, `asus-nb-wmi` bound), so profiles call `asusctl_install` unconditionally and non-fatally. Keep its package list inside the script: in a profile `*_functions` body `make audit-installation` would declare those packages for every machine. `--uninstall` removes only what its manifest lists, so do not install asusctl by hand over a managed copy. While `power-profiles-daemon` or `tuned` runs, it turns off `asusd`'s own AC/battery profile switching through D-Bus so the two do not fight over the platform profile; never stop or mask that daemon for it. Keep `is_supported_family` in step with `data/asusd.rules` of the pinned release when bumping `VERSION`/`COMMIT`. Agents preview with `make repair REPAIR=asusctl DRY_RUN=true` or `--status` and leave the real run (it uses `sudo` and compiles for minutes) to the user. `docs/ASUSCTL.md` has the design; `tests/test_asusctl_install.sh` covers it.
- **asusctl keyboard lighting**: `.local/scripts/asusctl_lighting.sh` is a step of its own, so a repair needs no `sudo` and it also works when asusctl came from elsewhere; profiles call `asusctl_lighting` non-fatally right after `asusctl_install`. It acts only when every `xyz.ljones.Aura` device that `asusd` exports lists the effect, because `asusctl aura effect` applies to all of them and aborts at the first refusal, and it confirms a change by reading `LedModeData` back. Rerunning it (bootstrap or `make repair REPAIR=asusctl-lighting`) re-asserts the configured effect over a hand-picked one, so change `EFFECT`/`SPEED`/`DIRECTION` in the script instead of fighting it. When bumping the asusctl pin, recheck `mode_number` and `MODE_DATA_SIGNATURE` against `AuraModeNum` and `LedModeData`. `REPAIR=keyboard` is the unrelated X11 key layout. Agents preview with `--dry-run` and leave the real run (it changes the keyboard) to the user. `docs/ASUSCTL.md` has the design; `tests/test_asusctl_lighting.sh` covers it.
- **`anime-gif-check` and the lid**: `.local/scripts/bin/anime-gif-check` (Python in `.local/scripts/anime_gif_check.py`) simulates the AniMe Vision lid and filters GIFs by legibility. It never starts `asusctl` (a test scans the source for process-launching calls) and writes only under `--out`, never over an existing file without `--force`. Playing a GIF turns the daemon's built-in animations off until `asusctl anime --enable-powersave-anim true`, so agents run the check and the tests and leave playing to the user. The thresholds come from measurements (`docs/ASUSCTL.md`, "Lid animations"): change one only with new measurements, and keep `STRIP_FLAGS` the single source of both the simulation and the printed `asusctl anime gif` flags. NumPy and Pillow stay optional like every Python helper here (PEP 668): without them the tool prints install hints and exits 2, and its tests skip. `tests/test_anime_gif_check.py` covers it with synthetic GIFs whose verdict is known by construction, and resolves the interpreter itself (see the `ARGV0` bullet).
- **`anime-toggle` and the lid**: a function in `.config/zsh/aliases`, defined only where `asusctl` and `busctl` exist and never an alias, because a toggle reads the lid's state first. Each run reads `EnableDisplay` and `Brightness` from `asusd` (`/xyz/ljones/aura/anime`, interface `xyz.ljones.Anime`), so a laptop without the display, a stopped daemon, or a reply that is not `b true|false` then `u N` gets a message and no change. The lid counts as lit only when it is enabled and brighter than Off, because `asusctl anime --brightness off` leaves `EnableDisplay` true: switching off sends `--enable-display false --brightness off`, switching on sends `--enable-display true` and raises an Off brightness to `med` (enabling a display whose brightness is Off shows nothing). It takes no argument on purpose: `anime-toggle off` would turn a dark lid on. It needs no `sudo`, and `asusd` stores the result in `/etc/asusd/anime.ron`. Agents verify with the test and toggle the real lid only when the user asks. `docs/ASUSCTL.md` has the design; `tests/test_anime_toggle.sh` covers it with a fake `busctl` and `asusctl` in clean Bash and Zsh shells.
- **AppImage terminals and `ARGV0`**: zsh uses an exported `ARGV0` as `argv[0]` of every command it runs, and Cursor, an AppImage, hands it to its shells, so Python started there reported the AppImage as `sys.executable` and anything that re-launched it (`subprocess.run([sys.executable, …])`, `multiprocessing` workers, the interpreter YouCompleteMe records) started the editor. `.zshenv` and `.config/zsh/.zshenv` carry an identical guard block that drops `ARGV0` when `$APPIMAGE` is set. Both files are needed: zsh reads `$ZDOTDIR/.zshenv` and skips `~/.zshenv` when `ZDOTDIR` is already set in its environment, as in Cursor's shells, and the guard must stay the first thing each file runs. `~/.config/zsh` is a folded symlink into this checkout, so the new file applies at once, but shells that were already running keep the old value until Cursor restarts. Tests of Python tooling still resolve the interpreter themselves instead of trusting `sys.executable`, and the `ycm.sh` check on the recorded interpreter stays as a second line of defence. `tests/test_zsh_argv0.sh` runs the real blocks in zsh, against a control that shows the quirk.
- **NVIDIA Container Toolkit**: `nvidia_container_toolkit_install` (in `base_functions`) installs it from NVIDIA's own apt repository on a machine with an NVIDIA GPU and skips every other one; only the `work` entrypoint calls it for now, non-fatally like `asusctl_install`. The GPU check reads sysfs (`nvidia_gpu_present`: vendor `0x10de`, display class `0x03xxxx`, so the card's HDMI audio function does not count), which works before the driver loads. Keep the package out of every `*_functions` body: `NVIDIA_CONTAINER_TOOLKIT_PACKAGES` is registered in `STANDALONE_INSTALLERS`, so the audit declares it where an entrypoint calls the step and never expects it on a machine without the GPU. The repository is flat (`Suites: /`, no `Components:`), and a release upgrade leaves its `.sources` file `Enabled: no`; the step rewrites it and retires a legacy `nvidia-container-toolkit.list`. It installs the package only: `nvidia-ctk runtime configure --runtime=docker` edits `/etc/docker/daemon.json` and needs a daemon restart, so the step just prints that command. `make repair REPAIR=nvidia-container-toolkit` repeats the step on any apt machine; agents preview it with `DRY_RUN=true` and leave the real run (`sudo`, apt) to the user. The uninstall function is `nvidia_ctk_uninstall` on purpose: the `uninstall_*` checklists show the function name as a tag column as wide as the longest name, and a name over 21 characters clips every other row's description. A stage added to `work_main` needs a stub in `tests/test_bootstrap_work.sh`, whose `sudo` guard fails the test instead of letting a forgotten stage rewrite `/etc/apt`. `tests/test_nvidia_container_toolkit.sh` covers it with a fake sysfs tree and stub commands.
- **OpenLogi** (Logitech Options+ alternative for Bolt and Unifying receivers; it cannot pair Lightspeed ones): `openlogi_install` (in `ubuntu_functions`) is called only by the `ubuntu` entrypoint, non-fatally as `openlogi_install ||` like `asusctl_install`. OpenLogi has no apt repository, so the step resolves the latest GitHub release (`OPENLOGI_VERSION=0.8.11` pins one) and installs its `.deb` only after `minisign` verifies it against the vendor key pinned in the function. That key is the trust anchor in `packaging/linux/install.sh` of `AprilNEA/OpenLogi`: check it there before changing it, and change the copy in `tests/test_openlogi_install.sh` with it. The shell ignores `set -e` inside a function called as `openlogi_install ||`, so every step is chained and a failure warns and returns 1. The audit shapes the code: `$apt minisign` stays alone on its line (the audit reads every word after a line-leading `$apt` as a package, so a trailing `|| return 1` would be declared as the packages `return` and `1`), the package file is `local openlogi_deb=` and mapped in `DEB_FILE_PACKAGES`, and no function is defined inside it (`function_bodies` ends a body at the first column-0 `}` and takes an indented `name() {` for a new function). Only one program may own a receiver, so OpenLogi conflicts with Solaar, and its per-application profiles need X11 or XWayland. Ubuntu 22.04 does not package `minisign`, and the step then stops before it downloads anything. Agents leave the real run (it uses `sudo` and the network) to the user; `tests/test_openlogi_install.sh` covers the step with stubs for `curl`, `minisign`, `dpkg`, `systemctl`, `sudo`, and `apt-get`.
- **kondo** (removes `node_modules`, `target`, `build` and other rebuildable folders from projects): `arch_functions` and `mac_functions` install it from their package managers (`kondo`). Ubuntu has no package, so `kondo_install` (in `ubuntu_functions`) installs the pinned release into `/usr/local/bin`, and only the `ubuntu` entrypoint calls it, non-fatally as `kondo_install ||` like `openlogi_install` (every step is chained, because the shell ignores `set -e` there). Upstream publishes no checksum file, so the function pins the SHA-256 of each Linux build (GitHub shows the same value as the asset digest: `gh api repos/tbillington/kondo/releases/tags/vX.Y.Z --jq '.assets[] | {name, digest}'`), and `sudo install` runs only after `sha256sum --check` passes. Bump `version` and both digests together, and change the copies in `tests/test_kondo_install.sh`, which fails until they agree. The `work`, `ubuntu-windows` and Gentoo profiles do not install it. kondo deletes for good and ignores Git (it asks before each project unless `--all` is given, and `--dry-run` only lists), so never run it on a repository unless the user asks. kondo 0.9 has no `--version` flag. `.local/README.md` has the details, and `tests/test_kondo_install.sh` covers the step with stub commands.
- **OpenShot and Blender** (video editors): `ubuntu` and `work` install the official snaps (`openshot-qt`, strictly confined, and `blender --classic`) from `snaps_install` and `gui_apps_install`, on `snap list X || sudo snap install X` lines the audit reads (it gives Blender's missing-package fix command `--classic`). Do not switch OpenShot to its PPA or the archive package: the PPA touches about 70 packages (OpenCV, GDAL, HDF5), ships `python3-openshot` as a daily build, and an Ubuntu release upgrade disables it, and the archive build is two releases behind. `arch` and `manjaro` install `openshot` and `blender` with pacman, `mac` the `openshot-video-editor` and `blender` casks, and the WSL profile neither. The snap's NVENC export is judged from its bundled FFmpeg and snapd's NVIDIA mounts, not from a real export. `.local/README.md` has the measurements; `tests/test_davinci_resolve_install.sh` covers the declarations in every profile and `tests/test_installation_audit.py` the audit's reading of them.
- **DaVinci Resolve** (free edition): `davinci_resolve_install` (in `base_functions`) runs `.local/scripts/davinci_resolve_install.sh` and only the `ubuntu` and `work` entrypoints call it, non-fatally as `davinci_resolve_install ||` (a missing ZIP is the normal state of a new machine). Blackmagic offers the download only behind a registration form, so the script never fetches it and never fills the form in: it finds `DaVinci_Resolve_<version>_Linux.zip` (or the `.run`) in the XDG download folder, `~/Downloads`, or `~`, or takes `--installer FILE`; do not add a download URL, a scraped token, or a mirror. It skips machines without an NVIDIA GPU (sysfs check, `--force` overrides) and ones that have `/opt/resolve/bin/resolve`, refuses root, and needs a terminal because Blackmagic's `.run -i` asks questions (`--unattended` stops before it instead of hanging). The ZIP is unpacked and checked before apt or sudo run, then come the prerequisites from `PREREQUISITE_PACKAGES` (Ubuntu 24.04+ `t64` names), `sudo env SKIP_PACKAGE_CHECK=1 ./….run -i`, the four bundled glib libraries moved to `/opt/resolve/libs/not_used` (reversible), and an `ldd` report of what is still missing. Keep that array inside the script, one name per line with no comments in it, and registered in `STANDALONE_INSTALLERS`, so the audit declares the libraries only where an entrypoint calls the step; `make audit-installation` does not check Resolve itself. `make repair REPAIR=davinci-resolve` repeats the step (`DRY_RUN=true` previews it). `davinci_uninstall` removes `/opt/resolve` only when `bin/resolve` exists, the launchers whose `Exec=` starts a program inside it, and the two udev rules the installer writes, never user data. The installer flow has only run against a fake `.run`: real Resolve 21 on Ubuntu 26.04 is unverified, so agents run the tests and `--dry-run` and leave the real run (`sudo`, a multi-gigabyte ZIP, questions) to the user. `.local/README.md` has the design; `tests/test_davinci_resolve_install.sh` covers it with stub commands and a real ZIP.
- **`update` and `updateall` steps**: both are functions over `_update_run`, not aliases. An alias appends typed arguments to its last command, so it cannot offer `--dry-run`/`--help`, and zsh-syntax-highlighting paints it red whenever any command inside it is not installed, however well guarded. They are functions rather than scripts because `updateall` runs `antigen update` and `antigen` is a function of the interactive zsh session. Run each new step through `_update_step`: it honors `--dry-run`, tallies failures, and never stops the steps after it (`--best-effort` keeps a step out of the summary when it fails only for having nothing to do, like `xcode-select --install`). Run every step in the foreground: `nvim +PlugUpdate` draws a full-screen UI, so the shell stops it as a background job (`suspended (tty output)`) before it updates anything. The Emacs package update is the one background job, because its window stays open. Never call `pip install --user` unconditionally: Debian/Ubuntu, Arch and Homebrew mark Python `EXTERNALLY-MANAGED` (PEP 668) and apt owns `python3-pynvim`, so `pip_user_upgrade` skips those interpreters (and virtualenvs); do not force it with `--break-system-packages`. On Arch and Manjaro run yay as `command yay -Syu` and detect the binary with the wrapper unset: `command -v yay` finds the `yay()` wrapper (`yay -S --noconfirm --needed`) even when yay is not installed. `tests/test_updateall.sh` covers it.
- **`git-recurse` summaries**: after its `Done:` line the script prints a summary chosen from the command. `git pull` lists the repositories it updated (HEAD is recorded around the command); `git status` lists the repositories that are not clean, as `2 modified, 1 untracked, ahead 1` (conflicted, staged, modified, untracked, ahead, behind, in that order; a path both staged and modified counts under each). `-S` forces one and `GIT_RECURSE_SUMMARY=0` turns both off. The status summary never reads the text the command printed, which is localized and may be `--short`: each job runs its own `git status --porcelain --branch` (`GIT_OPTIONAL_LOCKS=0`, same timeout) and `describe_status` parses that. It is plain shell because every repository runs at once and a program started per repository (an awk was measured) lengthens the whole run. `describe_status` answers 1 for "clean", so a probe or parse that fails fails the repository instead of passing as clean. The script colours with `tput` even when its output is captured, so `tests/test_git_recurse.sh` pins `TERM=dumb`; without that the test fails in any real terminal. The test loads the parser and the probe from the script to cover porcelain cases and the path without a `timeout` command (macOS), and runs the whole script on real repositories in each state. Mini carries a second copy of the script that runs the same tests (see the Mini `.bashrc` bullet), so a new behaviour belongs in the part of `tests/test_git_recurse.sh` that goes through the command alone.
- **Mini `.bashrc`** (`.local/Mini/.bashrc`): the portable file, copied by hand to `~/.bashrc` on a machine that has none of these dotfiles (like `.local/Mini/.gitconfig`), so it cannot source anything from the repository and carries condensed copies of the commands that matter there. A request to add an alias or command "everywhere" includes it. `clone-all`, `clone-team`, `git-recurse` and `git-ahead` are such copies: functions with a subshell body (`name() ( … )`, so `exit`, variables, inner functions, options, traps and descriptors never reach the interactive shell). The clone commands sit over two helpers, `_clone_repo_dir` and `_clone_configure_repo`, that copy `resolve_repo_dir` and `configure_tracked_repo_git` from `.local/scripts/lib/git-repo-defaults.sh`. Change an original and its Mini copy in the same run; `tests/test_mini_bashrc.sh` runs both side by side (the real `clone-all`, `clone-team` and `git-ahead` scripts and the library's identity, hooks and path rules, compared on output, errors, exit status, settings and hooks run) and fails when they drift. `git-recurse` is held to its whole suite instead: `tests/test_git_recurse.sh` takes the command from `GIT_RECURSE_UNDER_TEST`, and every test that goes through the command alone (all but the white-box tests of the script's own functions, after the early exit) must pass for the script and the copy alike, so add a behaviour test there, not in the Mini test. The patterns copied from the script (the transient-error list, the pull and status regexes) are compared word for word, so a change to one file fails until the other follows. The copy has every option and variable of the script except `-k` (it adds one Mac's ssh key), runs with or without `tput` and `timeout`/`gtimeout`, and avoids Bash features newer than 3.2 (macOS ships it as `/bin/bash`; no test runs on a real 3.2, so keep `mapfile`, `wait -n` and `${var^^}` out by hand). Put new code above the aliases section, because bash bakes an alias that is already defined into the body of a function parsed after it: the aliases `grep -i`, `mv -iv` and `rm -vI` are why these functions call `command grep`, `command mv` and `command rm`, and a test loads the file three times to catch a miss. `set keyseq-timeout 50` near the top overwrites the positional parameters of whoever sources the file, so a test passes data through the environment. `gr`, `gah` and `status` call these functions, so they work on a machine without the dotfiles. `gclean` is a condensed copy of `git-clean-branches` (no `--depth` or `--no-fetch`), and `git-ci-status`, a 479-line Python tool, has no Mini copy. `.local/scripts/lint_helpers.sh` lints it (`LINT_PATTERNS`).
- **Distro-specific antigen bundles**: the oh-my-zsh `archlinux` bundle loads only when `DISTRO` is `arch` or `manjaro` (guard in `.config/zsh/.zshrc`). Unguarded, it adds pacman/AUR aliases and helpers like `upgrade` and `paclist` that cannot work without `pacman`, and zsh-syntax-highlighting paints them red. Guard on `DISTRO`, not `command -v pacman`: Debian and Ubuntu ship a `pacman` arcade game in `/usr/games`. While `~/.config/antigen/init.zsh` exists, antigen ignores every `antigen bundle` call and replays that cache; it rebuilds only when `.zshrc` is newer than its `.zwc`, so a faked `DISTRO` in a real shell can poison the cache. Test guards with a stub antigen. `tests/test_zshrc_bundles.sh` covers it.
- **Profile detection and the `work` profile**: each bootstrap writes `~/.config/distro` (sourced by `.zshenv`), but `DISTRO` in it cannot name `work`: the shell config branches on `DISTRO=ubuntu` (`update` and `updateall` in `.config/zsh/aliases`, `.config/zsh/.zprofile`, `cleanup`), so `DISTRO=work` would make the OS update skip itself. `bootstrap/work` therefore also writes `export DOTFILES_PROFILE=work`. The two detectors, `detect_profile` in `.local/scripts/audit_installation.py` (behind `make audit-installation` and `make doctor`) and the one in `.local/scripts/repair-installation` (behind `REPAIR=vim`), read `DOTFILES_PROFILE` before `DISTRO`, ignore a commented-out or empty line, and fail with an error on a value that is not a profile instead of silently falling back to `DISTRO` (that fallback is the wrong-profile audit this prevents). Keep the two in step; `tests/test_profile_detection.py` runs the same distro files through both. A machine provisioned before the marker existed has none and is audited as `ubuntu`, which reports the desktop package set as missing, until the line is appended once: back up the file, then `printf 'export DOTFILES_PROFILE=work\n' >> ~/.config/distro` (re-running `bootstrap-work` only for that is unnecessary). The next bootstrap rewrites the file from scratch, so a marker cannot outlive a switch of profile.
- **`cleanup` steps**: `cleanup` is the script `.local/scripts/bin/cleanup`, not an alias or a function. An alias appends typed arguments to its last command, so it cannot offer `--dry-run`/`--help`; a function in `.config/zsh/aliases` needed `command` in front of every tool (this file aliases `df` to `df -h`, and the Arch/Manjaro `yay()` wrapper would run instead of `yay -Sc`); a script has neither problem and also runs from bash. Never define a `cleanup` function or alias here: it would shadow the script. Zsh puts `~/.local/scripts/bin` on `PATH` (`.zshenv`); plain bash does not, like `git-recurse`. Run new steps through `step`, which honors `--dry-run` (only read-only probes such as `docker info`, `snap list` and `docker volume ls` still run), tallies failures, and returns the command's failure. Prune Docker containers, then ask about volumes, then prune images and build cache (an image used by a stopped container survives the image prune, a volume used only by a stopped container is unused once it is gone, and the slow unattended prunes belong after the questions); probe the daemon once with `docker info`.
- **`cleanup` and Docker volumes**: volumes hold data that nothing rebuilds, so they are never pruned in bulk. Only a per-volume answer deletes: list `docker volume ls --filter dangling=true`, show size, age, origin and driver, default to No, and remove by name with `docker volume rm NAME`. Never `docker volume prune` and never `-f` (without it Docker refuses a volume that any container, even a stopped one, still references). Nothing is deleted under `--dry-run` or when stdin or stdout is not a terminal; Enter, `n`, `q`, an unreadable answer and end of input all keep the volume. The `l` answer lists a local volume from a throwaway container with a read-only, offline mount and `--pull never`, reusing a local image that has `ls`. The Docker CLI rewrites a literal `\t` or `\n` in `--format` before parsing it, so keep both outside `{{ }}`. `tests/test_cleanup.sh` covers all of it with stub commands, and a Python `pty` helper types the answers because the prompts only appear on a terminal.
- **`logout-all` and stored credentials**: `.local/scripts/bin/logout-all` signs out of browsers, editors and CLIs on a shared or work machine (plan, then ask, then apply; `--dry-run`, `--only`/`--skip` over the groups `cli files browsers apps history agents`) and `--audit` reports what is left, read-only. By default it stops no process: a running app is skipped because it would write its session back on exit, and without `pgrep` every app counts as running. `--close-apps` is the one opt-in exception: after the answer it sends SIGTERM, never SIGKILL, so the app saves as for a normal close, to the top process of each app that the plan listed (never to its helpers, which quit with it), waits up to `LOGOUT_ALL_CLOSE_WAIT` seconds (default 20), and skips whatever has not quit like any running app. It never closes the app that hosts its terminal (an ancestor of the script), one that started after the plan, or anything without `pgrep`; the single `kill -TERM` site is guarded by a test, so keep it the only one. It deletes only catalog paths inside `$HOME`, never follows a symbolic link, and never deletes SSH or GPG keys, API-key files, kubeconfig or `.env` files: `--audit` lists those for the user to decide. It never prints a secret value (`sed -n …p`, `grep -l`, key names and counts only), so keep new audit checks to that. Firefox's `key4.db` stays because it also holds imported client-certificate keys. The editors keep their login in `state.vscdb` next to chat history, so only the sign-in rows go, with `secure_delete` and `VACUUM` so no old copy stays in the file. `agents` runs last: `gh` needs the keyring unlocked to delete the token it keeps there. Offline, `gh` lists no account, so its `hosts.yml` is deleted instead (`GH_CONFIG_DIR` is the folder that holds `hosts.yml`; `XDG_CONFIG_HOME` holds a `gh` folder). `history` is opt-in because open shells write theirs back. A local sign-out cannot revoke a token that was copied, and anyone with sudo can read `$HOME` (the audit says whether the disk is encrypted). Agents run `--audit` and `--dry-run` (also with `--close-apps`) and leave the real run to the user, from a plain terminal; never run `--close-apps` for real, because it quits the user's browsers and editors. `tests/test_logout_all.sh` covers it with stub commands, a Python `pty` helper for the prompt, and fake-app processes for `--close-apps` whose `pgrep` shows nothing else, so a test can never signal a real app.
- **Git credential storage**: never set `credential.helper store`: it keeps HTTPS passwords and tokens unencrypted in `~/.git-credentials`, which anyone with sudo reads. The Ubuntu and Arch bootstraps call `git_credential_helper_configure` (`base_functions`) instead. It replaces a plaintext helper in the global config with `cache --timeout=28800` (held in memory, never on disk), adds that helper when none is set, leaves any helper that does not store in plain text alone (a keyring helper, `gh auth git-credential`), only warns on failure, and reports a leftover `~/.git-credentials` without deleting or printing it. The `work` profile does not touch Git credentials. A host-specific helper wins for its host, so `gh` keeps serving GitHub and the generic helper decides the other hosts; hosts it serves are asked for the password again after 8 hours (`gh auth setup-git` gives GitHub its own helper). `make audit-installation` flags a plaintext helper as drift, `logout-all` deletes a leftover `~/.git-credentials`, and `logout-all --audit` lists remote URLs that embed a token (`add_pat` writes them). `tests/test_git_credential_helper.sh` and `tests/test_installation_audit.py` cover it.
- **`vault-secret` and the age identity**: the vault's credentials are SOPS + age, so whoever holds the age identity reads all of them, and a plain `~/.config/sops/age/keys.txt` is readable by anyone with sudo. On this work laptop keep it as `keys.txt.gpg` (`vault-secret key-wrap`): the helper points sops at it through `SOPS_AGE_KEY_CMD='gpg --quiet --batch --decrypt <path>'`, but only when none of `SOPS_AGE_KEY`, `SOPS_AGE_KEY_FILE` and `SOPS_AGE_KEY_CMD` is set and the plain file is absent, and `logout-all` already makes gpg-agent forget the passphrase. sops reads that variable as shell words without running a shell, so the path is single-quoted (`'\''` for a quote) and `$VAR` or a pipe never works in it. `key-wrap` takes the identity from stdin or a hidden prompt and keeps it only in shell memory and pipes (never an argument, a here-string, `echo` or a file), saves nothing unless the new copy alone opens the store (checked with `XDG_CONFIG_HOME` pointing at an empty folder, so a default `keys.txt` cannot hide a wrong key), and never overwrites or deletes a key. The lookup order is duplicated in the vault's Obsidian plugin and `.scripts/secrets_check.py`; change the three together. Agents run `vault-secret list` and the tests only: `key-status` can open a passphrase dialog and an entry prints a secret into the transcript. `tests/test_vault_secret.sh` covers it with stub commands and, when sops, age-keygen and gpg exist, with the real ones, a throwaway key, a throwaway `GNUPGHOME` and a stub pinentry.
- **Packages installed outside the bootstrap**: `audit_extra_packages` in `audit_installation.py` is the reverse of the package check. It reports what each manager says was installed on request (`apt-mark showmanual`, `snap list`, `pacman -Qqe`, `brew leaves` and casks) but no active bootstrap function declares, only for managers the profile declares packages for, as `[NOTICE]` findings that never change the exit code (`--list-extra` prints them as `manager:name`). A notice carries a `Fix:` command only when it is safe to paste. A `.deb` installed through a variable and a standalone installer's package array are invisible to `expected_packages`, so `DEB_FILE_PACKAGES` maps each `local <name>_deb=` variable of the bootstrap to its package (a new one needs an entry; `tests/test_audit_extra_packages.py` fails without it) and `STANDALONE_INSTALLERS` names the script array of each installer a profile calls (asusctl, and the NVIDIA Container Toolkit's array in `base_functions`). apt marks hundreds of OS packages as manual, so a removal command may name only an apt package that a `Requested-By` transaction in the retained apt logs installed on request (not `automatic`), a snap that Canonical does not publish, and nothing that matches `SYSTEM_PACKAGE_PATTERNS` (kernel, boot loader, firmware, drivers); the rest get a notice of their own with no command, because a pasted `apt-get remove language-pack-en` is not a suggestion to make. The commands stay interactive (`sudo apt-get remove`, `sudo snap remove`, `sudo pacman -Rs`, `brew uninstall`): never add `-y`, `--noconfirm` or `--purge`, and never use `yay`, whose zsh wrapper turns every call into an install. A package is kept by declaring it in the bootstrap or by listing `manager:name` in `~/.config/dotfiles/known-extra-packages` (per machine, outside the repository). The report wraps to the terminal (`output_width`, 60 to 100 columns) with a hanging indent and breaks the command with `\` so it still pastes as one command; `Reporter.result` accepts a multi-line message for this, so never print a package list as one unwrapped line. Only the apt and snap paths have run on a real machine; pacman and Homebrew are covered with stubs. `tests/test_audit_extra_packages.py` covers it.
- **Apps installed outside the bootstrap**: `audit_self_installed_apps` in `audit_installation.py` covers what the package check cannot see. An app that came with its own installer (an AppImage, Zed's `install.sh`, GPT4All's installer) is in no package manager's database, but it leaves a launcher in `$XDG_DATA_HOME/applications` (`~/.local/share/applications`), so that is what the audit reads. One `[NOTICE]`, which never changes the exit code, lists each application launcher (`Type=Application`, not `Hidden=true`) whose program exists and lies inside `$HOME` once symbolic links are followed, so `~/.local/bin/code` pointing at a system package and a launcher left behind for a deleted program do not count. Only the `[Desktop Entry]` group is read, because a `[Desktop Action …]` group has an `Exec` and a `Name` of its own. An `env VAR=value` prefix is skipped, a bare command name is looked up on `PATH`, and a program that cannot be told (`sh -c '…'`, a relative path, unbalanced quotes) is skipped. A launcher is declared when an uncommented line of the profile's entrypoint, or of a function it reaches (`active_bootstrap_code`, the same reading as the package check), names its file with word boundaries (`names_file`), as `ai_tools_install` does for `cursor.desktop` and `antigravity.desktop` on `arch`; a commented-out block and an uncalled function declare nothing. An installer that writes its own launcher (Zed's) is not recognized that way, so accept such an app by listing `app:KEY` (the launcher's file name without `.desktop`; the bare key works too) in `~/.config/dotfiles/known-extra-packages`. `--list-extra` prints the apps as `app:KEY` after the packages, so appending its output accepts everything at once. The audit deletes nothing. Under an app it prints a `Fix:` command only where the place of the program proves what belongs to the app (`app_location`), and nothing under any other app, whose owner uses its own uninstaller or deletes it by hand. The proof is one of: an AppImage (`.appimage` in any case, a file) is the file alone; a folder directly in `~/.local/opt`, `~/.opt`, `~/opt` or `~/Applications` is the app; so is a `*.app` bundle directly in `~/.local` (Zed's `install.sh`; a plain `~/.local/<x>` is shared with pipx and cargo and proves nothing); so is the nearest folder below `$HOME` that holds a Qt Installer Framework `maintenancetool` or `MaintenanceTool` (GPT4All, the Qt SDK). The home folder, a folder that holds apps, `~/.local/bin`, `~/bin` and any folder named like a part of a prefix (`bin`, `lib`, `share`, …) are never the result, so a script in `~/.local/bin` or a program in a folder of the owner's own gets no command. `app_files` adds the symbolic links in `~/.local/bin` and `~/bin` that lead into the app and every `.desktop` file that starts a program inside it, in the launcher folder and on the desktop (`user_desktop_dir`: `XDG_DESKTOP_DIR` of `user-dirs.dirs`, `~/Desktop` by default; the Qt installer leaves a shortcut there). The command is `rm -rI -- PATH…` (`removal_words`): `-I` asks once before a recursive removal and still asks when the answer comes from a pipe, it never has `-f` or `sudo`, and it names the app, its links and its launchers but never its settings or data (`~/.config/zed`, `~/.local/share/nomic.ai`), which the owner decides on. A path inside `$HOME` is written `~/…` when `SHELL_SAFE_PATH` needs no quoting; any other is quoted whole and written in full, because a tilde inside quotes is not expanded (`shell_path`, which also covers a `$HOME` that is a symbolic link, as `/home -> /var/home`). A wrong folder in `app_location` is a deleted folder, so never widen it to a guess: a new layout needs a test of the layout that gets a command and of the lookalike that gets none. A tool without a launcher stays invisible. Name every new `audit_*` function that `main()` calls in `MainTests.AUDITS` (`tests/test_audit_extra_packages.py`), or its tests run that audit against the machine's own files. `tests/test_audit_self_installed_apps.py` covers it with a fake home, a fake repository and real files, and runs the printed command with `bash` (answering `y`, `n`, an empty line and end of input) to check that the neighbours of the app survive.

## Workspace integration (cuberhaus multi-root)

The sibling [cuberhaus-workspace/](../cuberhaus-workspace/) repo holds the files that live at the workspace root (`~/cuberhaus`) but couldn't otherwise be versioned, because that root is a plain folder collecting ~50 sibling repos. `make workspace` is the single maintenance command: it syncs central files, then rebuilds `repos.json`.

The `cuberhaus-workspace/` repo is the single source of truth on both Windows (via WinDotfiles) and Linux (via this repo); only the sync driver invocation differs (`sync.sh` here, `sync.ps1` on Windows). See [../cuberhaus-workspace/README.md](../cuberhaus-workspace/README.md).
