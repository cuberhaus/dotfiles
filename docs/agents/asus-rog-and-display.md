# ASUS ROG G635LX hardware and display scale

Read before changing `asusctl_install`, `asusctl_lighting`, `brightness_fix`, `anime-gif-check`, `anime-toggle`, or `match-monitor-scales`, or before diagnosing brightness, keyboard lighting, the AniMe lid, or mixed-scale fullscreen jitter on the G635LX. Agents preview with `--dry-run` and leave runs that change hardware or display state to the user.

- **asusctl**: `.local/scripts/asusctl_install.sh` builds a pinned release and gates itself on the hardware (ASUS vendor, a family `asusd` supports, kernel 6.19+, `asus-nb-wmi` bound), so profiles call `asusctl_install` unconditionally and non-fatally. Keep its package list inside the script: in a profile `*_functions` body `make audit-installation` would declare those packages for every machine. `--uninstall` removes only what its manifest lists, so do not install asusctl by hand over a managed copy. While `power-profiles-daemon` or `tuned` runs, it turns off `asusd`'s own AC/battery profile switching through D-Bus so the two do not fight over the platform profile; never stop or mask that daemon for it. Keep `is_supported_family` in step with `data/asusd.rules` of the pinned release when bumping `VERSION`/`COMMIT`. Agents preview with `make repair REPAIR=asusctl DRY_RUN=true` or `--status` and leave the real run (it uses `sudo` and compiles for minutes) to the user. `docs/ASUSCTL.md` has the design; `tests/test_asusctl_install.sh` covers it.
- **asusctl keyboard lighting**: `.local/scripts/asusctl_lighting.sh` is a step of its own, so a repair needs no `sudo` and it also works when asusctl came from elsewhere; profiles call `asusctl_lighting` non-fatally right after `asusctl_install`. It acts only when every `xyz.ljones.Aura` device that `asusd` exports lists the effect, because `asusctl aura effect` applies to all of them and aborts at the first refusal, and it confirms a change by reading `LedModeData` back. Rerunning it (bootstrap or `make repair REPAIR=asusctl-lighting`) re-asserts the configured effect over a hand-picked one, so change `EFFECT`/`SPEED`/`DIRECTION` in the script instead of fighting it. When bumping the asusctl pin, recheck `mode_number` and `MODE_DATA_SIGNATURE` against `AuraModeNum` and `LedModeData`. `REPAIR=keyboard` is the unrelated X11 key layout. Agents preview with `--dry-run` and leave the real run (it changes the keyboard) to the user. `docs/ASUSCTL.md` has the design; `tests/test_asusctl_lighting.sh` covers it.
- **`anime-gif-check` and the lid**: `.local/scripts/bin/anime-gif-check` (Python in `.local/scripts/anime_gif_check.py`) simulates the AniMe Vision lid and filters GIFs by legibility. It never starts `asusctl` (a test scans the source for process-launching calls) and writes only under `--out`, never over an existing file without `--force`. Playing a GIF turns the daemon's built-in animations off until `asusctl anime --enable-powersave-anim true`, so agents run the check and the tests and leave playing to the user. The thresholds come from measurements (`docs/ASUSCTL.md`, "Lid animations"): change one only with new measurements, and keep `STRIP_FLAGS` the single source of both the simulation and the printed `asusctl anime gif` flags. NumPy and Pillow stay optional like every Python helper here (PEP 668): without them the tool prints install hints and exits 2, and its tests skip. `tests/test_anime_gif_check.py` covers it with synthetic GIFs whose verdict is known by construction, and resolves the interpreter itself (see the `ARGV0` bullet in [shell-tools.md](shell-tools.md)).
- **`anime-toggle` and the lid**: a function in `.config/zsh/aliases`, defined only where `asusctl` and `busctl` exist and never an alias, because a toggle reads the lid's state first. Each run reads `EnableDisplay` and `Brightness` from `asusd` (`/xyz/ljones/aura/anime`, interface `xyz.ljones.Anime`), so a laptop without the display, a stopped daemon, or a reply that is not `b true|false` then `u N` gets a message and no change. The lid counts as lit only when it is enabled and brighter than Off, because `asusctl anime --brightness off` leaves `EnableDisplay` true: switching off sends `--enable-display false --brightness off`, switching on sends `--enable-display true` and raises an Off brightness to `med` (enabling a display whose brightness is Off shows nothing). It takes no argument on purpose: `anime-toggle off` would turn a dark lid on. It needs no `sudo`, and `asusd` stores the result in `/etc/asusd/anime.ron`. Agents verify with the test and toggle the real lid only when the user asks. `docs/ASUSCTL.md` has the design; `tests/test_anime_toggle.sh` covers it with a fake `busctl` and `asusctl` in clean Bash and Zsh shells.
- **ROG brightness**: on the G635LX in dGPU/MUX mode `nvidia_wmi_ec_backlight` is a ghost device (values are accepted, the panel ignores them), so brightness tools writing to it appear to do nothing. The fix is `acpi_backlight=native` from `.local/scripts/brightness_fix.sh`; keep it after `shutdown_fix` in the `work` bootstrap and read `docs/ROG-BRIGHTNESS-DIAGNOSIS.md` before changing it.
- **`match-monitor-scales` and the mixed-scale wiggle**: on the G635LX under GNOME on Wayland, Chromium-based apps (Cursor, VS Code, Chrome, Obsidian) jitter in fullscreen on the external monitor whenever it runs at a different scale than the fractional laptop panel (133% beside 100% shook; 100%/100% and 133%/133% did not, in an A-B-A test), so keep every monitor at one scale. `.local/scripts/bin/match-monitor-scales` (a bash wrapper over the stdlib Python module `.local/scripts/match_monitor_scales.py`) gives all connected monitors the primary monitor's scale (`--scale` picks another) and recomputes their positions, because a scale change alters a monitor's logical size. No bootstrap runs it: it reads mutter's state over D-Bus with `busctl` (systemd) and applies with `gdctl` (package `mutter-common-bin`), and the user runs it by hand after a dock reconnect or a change in Settings. Keep these rules: `gdctl set --verify` always runs first and has the last word; the layout mode is never passed to `gdctl` (it errors when mutter cannot change it); flipped and leased monitors are refused (`gdctl` numbers flipped transforms differently from mutter); `--persistent` copies `~/.config/monitors.xml` to a new `.bak-DATE-TIME` file first and never overwrites a copy, then confirms the save by polling the file's content, because mutter writes it about two seconds later (`MATCH_MONITOR_SCALES_WAIT` sets the wait); the module has one `subprocess.run` call site and no shell, `sudo` or `pkexec` (a test scans the source); unknown words exit 2; and the help text of the wrapper and of the module must stay identical (a test compares them). `~/.config/monitors.xml` is GNOME's own per-machine file and is not stowed; mutter matches a saved layout by connector and monitor, so a monitor on another dock port needs its own `--persistent` run. Agents run `--dry-run` and the tests and leave the real run (it changes the live display, and `--persistent` the saved layout) to the user. Which side owns the bug, Chromium or mutter, is not known. `docs/FULLSCREEN-WIGGLE-DIAGNOSIS.md` has the evidence and the rollback; `tests/test_match_monitor_scales.py` covers the command with a fake `busctl` and `gdctl` and resolves the interpreter itself (see the `ARGV0` bullet in [shell-tools.md](shell-tools.md)).
