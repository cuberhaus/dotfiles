# DaVinci Resolve

Read before changing `davinci_resolve_install`, `.local/scripts/davinci_resolve_install.sh`, `davinci_uninstall`, or `.local/share/DaVinciResolve/configs/config.user.xml`, and before installing Resolve. Never loosen the udev override: it keeps raw HID devices from becoming writable by every local process.

- **DaVinci Resolve** (free edition): `davinci_resolve_install` (in `base_functions`) runs `.local/scripts/davinci_resolve_install.sh` and only the `ubuntu` and `work` entrypoints call it, non-fatally as `davinci_resolve_install ||` (a missing ZIP is the normal state of a new machine). Blackmagic offers the download only behind a registration form, so the script never fetches it and never fills the form in: it finds `DaVinci_Resolve_<version>_Linux.zip` (or the `.run`) in the XDG download folder, `~/Downloads`, or `~`, or takes `--installer FILE`; do not add a download URL, a scraped token, or a mirror. It skips machines without an NVIDIA GPU (sysfs check, `--force` overrides) and ones that have `/opt/resolve/bin/resolve`, refuses root, and needs a terminal because Blackmagic's `.run -i` asks questions (`--unattended` stops before it instead of hanging). The ZIP is unpacked and checked before apt or sudo run, then come the prerequisites from `PREREQUISITE_PACKAGES` (the whole list that the `AppRun` of Resolve 21.1.1 checks on Ubuntu, under the `t64` names of Ubuntu 24.04+; keep it complete instead of trusting the `ldd` report, because the Qt xcb plugin and `libQt5XcbQpa.so.5` do not link `libxcb-damage0`, which Blackmagic requires and the first version left out), the **udev override** (next sentence), `sudo env SKIP_PACKAGE_CHECK=1 ./….run -i`, the four bundled glib libraries moved to `/opt/resolve/libs/not_used` (reversible), an `ldd` report of what is still missing, and a check that no `/dev/hidraw*` is writable by every user. The udev override is a security control: Blackmagic's `post_install.sh` writes `/usr/lib/udev/rules.d/75-davincipanel.rules` with a rule `KERNEL=="hidraw*", MODE="0777"` that is not limited to Blackmagic hardware, so every raw HID device (touchpad, keyboard interfaces, security keys) becomes writable by every local process. Before the installer runs, the script writes `/etc/udev/rules.d/75-davincipanel.rules` (a file there replaces the file of the same name under `/usr/lib`) with only the Blackmagic USB rule, so no device is exposed in between and an upgrade cannot bring the rule back. It never overwrites an existing file or link of that name, stops the installation when it cannot write the file (rather than installing the rule it prevents), and `--keep-vendor-udev-rules` opts out. Never loosen it, and keep `BLACKMAGIC_VENDOR_MATCH`, `DONGLE_VENDOR_MATCH` and `OVERRIDE_MARKER` in step with what the vendor installer writes when a release changes. Keep the array inside the script, one name per line with no comments in it, and registered in `STANDALONE_INSTALLERS`, so the audit declares the libraries only where an entrypoint calls the step; `make audit-installation` does not check Resolve itself. `make repair REPAIR=davinci-resolve` repeats the step (`DRY_RUN=true` previews it). `davinci_uninstall` removes `/opt/resolve` only when `bin/resolve` exists, the launchers whose `Exec=` starts a program inside it (including `~/Desktop/com.blackmagicdesign.resolve.desktop`), Resolve's two menu files, and the udev rules the installer writes (`75-davincipanel.rules`, `75-davincikb.rules`, `75-sdx.rules`, plus the override), never user data. A rules file goes only when it names Blackmagic's USB vendor ID (`1edb`, or `096e` for the dongle) or carries the script's mark, so a same-named file of someone else stays; the `99-*` names are the ones in Blackmagic's payload, kept for an older or manual install. It leaves the shared places the installer wrote to (panel libraries in `/usr/lib64`, `/var/BlackmagicDesign`, icons, MIME types, the OFX renderer) and says so. The installer flow has only run against a fake `.run`: real Resolve 21 on Ubuntu 26.04 is unverified, so agents run the tests and `--dry-run` and leave the real run (`sudo`, a multi-gigabyte ZIP, questions) to the user. Resolve's interface size is its own `DisplayScale` preference (`~/.local/share/DaVinciResolve/configs/config.user.xml`: 100, 150, 200, or -1 for the system), which it turns into Qt's scale at start-up, so a launcher or wrapper that sets `QT_SCALE_FACTOR` does nothing (measured) and must not be added; under GNOME's `xwayland-native-scaling` an X11 program sees the screen at 2x the logical size, so a 133% panel wants 200%. The first window, the Project Manager, is borderless, modal, and on top by Resolve's own X11 hints. That file is tracked as `.local/share/DaVinciResolve/configs/config.user.xml` and linked by Stow, and it is the only path of `~/.local/share/DaVinciResolve` that `.gitignore` allows (the Project Library, LUTs, Fusion data and logs are app data): never widen the allow-list. Where the folder is missing Stow links the whole folder into the checkout, so `stow-backup-conflicts` first creates `~/.local/share/DaVinciResolve/configs` as a real folder (`REAL_FOLDERS`; `--dry-run` creates nothing) and `tests/test_stow_conflicts.sh` covers that against the real Stow, with a control that shows the fold. `200` is the value for the 133% panel of the G635LX and is one shared setting, so another machine's value is a deliberate change of that file. Whether Resolve writes through the link or replaces it when it saves Preferences is untested; a plain file there is an ordinary Stow conflict. Edit the file only while Resolve is closed, after a backup, and let the user make the call. `.local/README.md` has the design; `tests/test_davinci_resolve_install.sh` covers it with stub commands and a real ZIP.
