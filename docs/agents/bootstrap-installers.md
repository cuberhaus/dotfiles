# Bootstrap installers and profiles

Read before changing a file under `.local/scripts/bootstrap/`, adding an installer step or a package, registering a vendor apt source, or touching profile detection (`DOTFILES_PROFILE`, `detect_profile`). Agents leave the real runs (`sudo`, apt, network) to the user.

- **Vendor apt repositories**: register them only through `apt_vendor_source_ensure` / `ide_apt_sources_ensure` in `base_functions` (deb822 `.sources`, written after the signing key is verified); never hand-write a legacy `.list`. A flat repository (a suite ending in `/`, like NVIDIA's) passes an empty COMPONENTS argument, which leaves out the `Components:` line apt rejects there. An Ubuntu release upgrade disables third-party sources and the weekly `apt-get full-upgrade` then skips their packages silently, which is why `make audit-installation` checks the IDE packages and `make repair REPAIR=ide-repos` fixes them. Agents preview that repair with `DRY_RUN=true` and leave the real run (it uses `sudo`) to the user.
- **NVIDIA Container Toolkit**: `nvidia_container_toolkit_install` (in `base_functions`) installs it from NVIDIA's own apt repository on a machine with an NVIDIA GPU and skips every other one; only the `work` entrypoint calls it for now, non-fatally like `asusctl_install`. The GPU check reads sysfs (`nvidia_gpu_present`: vendor `0x10de`, display class `0x03xxxx`, so the card's HDMI audio function does not count), which works before the driver loads. Keep the package out of every `*_functions` body: `NVIDIA_CONTAINER_TOOLKIT_PACKAGES` is registered in `STANDALONE_INSTALLERS`, so the audit declares it where an entrypoint calls the step and never expects it on a machine without the GPU. The repository is flat (`Suites: /`, no `Components:`), and a release upgrade leaves its `.sources` file `Enabled: no`; the step rewrites it and retires a legacy `nvidia-container-toolkit.list`. It installs the package only: `nvidia-ctk runtime configure --runtime=docker` edits `/etc/docker/daemon.json` and needs a daemon restart, so the step just prints that command. `make repair REPAIR=nvidia-container-toolkit` repeats the step on any apt machine; agents preview it with `DRY_RUN=true` and leave the real run (`sudo`, apt) to the user. The uninstall function is `nvidia_ctk_uninstall` on purpose: the `uninstall_*` checklists show the function name as a tag column as wide as the longest name, and a name over 21 characters clips every other row's description. A stage added to `work_main` needs a stub in `tests/test_bootstrap_work.sh`, whose `sudo` guard fails the test instead of letting a forgotten stage rewrite `/etc/apt`. `tests/test_nvidia_container_toolkit.sh` covers it with a fake sysfs tree and stub commands.
- **OpenLogi** (Logitech Options+ alternative for Bolt and Unifying receivers; it cannot pair Lightspeed ones): `openlogi_install` (in `ubuntu_functions`) is called only by the `ubuntu` entrypoint, non-fatally as `openlogi_install ||` like `asusctl_install`. OpenLogi has no apt repository, so the step resolves the latest GitHub release (`OPENLOGI_VERSION=0.8.11` pins one) and installs its `.deb` only after `minisign` verifies it against the vendor key pinned in the function. That key is the trust anchor in `packaging/linux/install.sh` of `AprilNEA/OpenLogi`: check it there before changing it, and change the copy in `tests/test_openlogi_install.sh` with it. The shell ignores `set -e` inside a function called as `openlogi_install ||`, so every step is chained and a failure warns and returns 1. The audit shapes the code: `$apt minisign` stays alone on its line (the audit reads every word after a line-leading `$apt` as a package, so a trailing `|| return 1` would be declared as the packages `return` and `1`), the package file is `local openlogi_deb=` and mapped in `DEB_FILE_PACKAGES`, and no function is defined inside it (`function_bodies` ends a body at the first column-0 `}` and takes an indented `name() {` for a new function). Only one program may own a receiver, so OpenLogi conflicts with Solaar, and its per-application profiles need X11 or XWayland. Ubuntu 22.04 does not package `minisign`, and the step then stops before it downloads anything. Agents leave the real run (it uses `sudo` and the network) to the user; `tests/test_openlogi_install.sh` covers the step with stubs for `curl`, `minisign`, `dpkg`, `systemctl`, `sudo`, and `apt-get`.
- **kondo** (removes `node_modules`, `target`, `build` and other rebuildable folders from projects): `arch_functions` and `mac_functions` install it from their package managers (`kondo`). Ubuntu has no package, so `kondo_install` (in `ubuntu_functions`) installs the pinned release into `/usr/local/bin`, and only the `ubuntu` entrypoint calls it, non-fatally as `kondo_install ||` like `openlogi_install` (every step is chained, because the shell ignores `set -e` there). Upstream publishes no checksum file, so the function pins the SHA-256 of each Linux build (GitHub shows the same value as the asset digest: `gh api repos/tbillington/kondo/releases/tags/vX.Y.Z --jq '.assets[] | {name, digest}'`), and `sudo install` runs only after `sha256sum --check` passes. Bump `version` and both digests together, and change the copies in `tests/test_kondo_install.sh`, which fails until they agree. The `work`, `ubuntu-windows` and Gentoo profiles do not install it. kondo deletes for good and ignores Git (it asks before each project unless `--all` is given, and `--dry-run` only lists), so never run it on a repository unless the user asks. kondo 0.9 has no `--version` flag. `.local/README.md` has the details, and `tests/test_kondo_install.sh` covers the step with stub commands.
- **OpenShot and Blender** (video editors): `ubuntu` and `work` install the official snaps (`openshot-qt`, strictly confined, and `blender --classic`) from `snaps_install` and `gui_apps_install`, on `snap list X || sudo snap install X` lines the audit reads (it gives Blender's missing-package fix command `--classic`). Do not switch OpenShot to its PPA or the archive package: the PPA touches about 70 packages (OpenCV, GDAL, HDF5), ships `python3-openshot` as a daily build, and an Ubuntu release upgrade disables it, and the archive build is two releases behind. `arch` and `manjaro` install `openshot` and `blender` with pacman, `mac` the `openshot-video-editor` and `blender` casks, and the WSL profile neither. The snap's NVENC export is judged from its bundled FFmpeg and snapd's NVIDIA mounts, not from a real export. `.local/README.md` has the measurements; `tests/test_davinci_resolve_install.sh` covers the declarations in every profile and `tests/test_installation_audit.py` the audit's reading of them.
- **Caffeine indicator autostart**: the apt package `caffeine` autostarts only its headless daemon (`/etc/xdg/autostart/caffeine.desktop` runs `/usr/bin/caffeine`, which suspends the screensaver while a window is full screen). The tray toggle is a separate program, `/usr/bin/caffeine-indicator`, with no autostart entry, so `caffeine_indicator_autostart_install` (in `base_functions`) writes `~/.config/autostart/caffeine-indicator.desktop`. The `ubuntu` and `work` entrypoints call it right after the step that installs the package, non-fatally as `caffeine_indicator_autostart_install ||`, and each `*_gui_uninstall` removes the file. Do not track the entry under `.config/autostart/` in the checkout: `~/.config/autostart` is shared by every app that starts at login, so Stow would link the whole folder into the repository and each of those apps would write its entry there (the `REAL_FOLDERS` list in `stow-backup-conflicts` exists for that kind of folder, but a bootstrap-written file needs none of it). `TryExec` makes the session skip the entry once the package is gone, and an entry that differs is kept as `caffeine-indicator.desktop.bak` before it is replaced. `arch` and `manjaro` install `caffeine-ng`, a different program, and `mac` the Caffeine cask, so neither calls the helper. `tests/test_caffeine_autostart.sh` covers the helper with a sandbox home, and `tests/test_bootstrap_work.sh` the stage's place in `work_main`.
- **Profile detection and the `work` profile**: each bootstrap writes `~/.config/distro` (sourced by `.zshenv`), but `DISTRO` in it cannot name `work`: the shell config branches on `DISTRO=ubuntu` (`update` and `updateall` in `.config/zsh/aliases`, `.config/zsh/.zprofile`, `cleanup`), so `DISTRO=work` would make the OS update skip itself. `bootstrap/work` therefore also writes `export DOTFILES_PROFILE=work`. The two detectors, `detect_profile` in `.local/scripts/audit_installation.py` (behind `make audit-installation` and `make doctor`) and the one in `.local/scripts/repair-installation` (behind `REPAIR=vim`), read `DOTFILES_PROFILE` before `DISTRO`, ignore a commented-out or empty line, and fail with an error on a value that is not a profile instead of silently falling back to `DISTRO` (that fallback is the wrong-profile audit this prevents). Keep the two in step; `tests/test_profile_detection.py` runs the same distro files through both. A machine provisioned before the marker existed has none and is audited as `ubuntu`, which reports the desktop package set as missing, until the line is appended once: back up the file, then `printf 'export DOTFILES_PROFILE=work\n' >> ~/.config/distro` (re-running `bootstrap-work` only for that is unnecessary). The next bootstrap rewrites the file from scratch, so a marker cannot outlive a switch of profile.
