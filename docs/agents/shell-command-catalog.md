# Shell command catalog and the `-h` rule

Read before adding or changing an alias, function, or script in `.config/zsh/aliases`, `.config/zsh/functions`, or `.local/scripts/bin`.

- The interactive `commands` function in `.config/zsh/functions` builds the catalog from annotations in the files themselves; do not maintain a second hardcoded catalog. It groups by purpose, not by kind, and asks the live shell which names exist, so a definition behind a failed `if` (an Arch-only alias on Ubuntu) is not listed. `commands WORD...` filters by name, group, description, or what an alias runs; `-v` adds what each alias runs and where each function and script lives; names that start with `_` are internal helpers, shown only with `-a`; `commands --list` prints one tab-separated line per command (kind, name, group, expansion, source) for scripts and tests.
- Put aliases and small shell wrappers in `.config/zsh/aliases`, reusable functions in `.config/zsh/functions`, and standalone executables in `.local/scripts/bin`. A name defined as more than one kind is listed once, as the one the shell runs (alias, then function, then script), and `-v` says what it hides.
- A `##@ Group name` line starts a group for the aliases and functions below it, up to the next `##@`; each file starts with none. Name groups by purpose (`Git`, `Packages & updates`). Entries with no group are listed last under **Other**, and groups appear in the order they first show up: aliases, then functions, then scripts.
- Add a concise behavioral description immediately above every alias and function using a `##` documentation comment. Plain `#` comments and blank lines may sit between it and the definition; any code line in between drops it. The catalog supports `alias name=`, `name()`, `name ()`, `function name()`, and `function name {`, and a name defined twice (an alias in each branch of an `if`) keeps the first description:

  ```bash
  ##@ Git across repositories

  ## Show git status for every repository below the current directory.
  status() { git-recurse "$@" git status; }
  ```

- An alias without a `##` line is listed as `(no description)`; write the line instead of relying on that. An alias that only renames one command (`gr="git-recurse"`) and has no description is folded into that command's entry as `git-recurse (gr)`, and one that starts with its own name (`grep='grep -i --color=auto'`) also shows the options it adds.
- Start each executable in `.local/scripts/bin` (an executable regular file directly in that folder) with `# Description: ...` and `# Group: ...` comments after the shebang; the catalog uses them as the command's description and group. The header ends at the first line that is neither blank nor a comment.
- Keep descriptions imperative, behavior-focused, and short enough to scan. Do not describe only the implementation location or repeat the command name.
- **Every command answers `-h` and `--help`.** A script or function checks for them first, before any dependency check, argument handling, or action, prints `Usage: NAME ...` and what the command does on stdout, and exits 0 (`return 0` in a function) with nothing on stderr. An alias hands every word you type to its last command, so it is a safe shortcut only when it is one simple command: a chain (`a; b`, `a && b`, a pipe, a trailing `&`) has already run its first part when `-h` arrives, and fixed arguments of one of our scripts (`restore-app-data anki --apply`) come before yours and can swallow it. Make those a function that answers `-h` itself, or a script (`yolo` is a script for that reason). An alias of one of our commands reaches that command's help, an alias of another program leaves `-h` to that program (`ls`, `grep`) except `ssh` and the browsers with a fixed host or address, where what you add lands after it as a remote command or another page (`erag-tunnel` and `erag-chrome` are functions for that reason), and an alias of a git subcommand must leave the repository alone for `-h` (`git commit -m` would take it as the message, so `gc` is a function). A command that acts and has no use for an extra argument refuses it instead of treating it as data: `yolo --dry-run` must not push, and `add_pat` and `clone-all` refuse a word that starts with `-`.
- When an alias becomes a function, put `unalias NAME 2>/dev/null` before the definition. A shell that loaded the old file still has the alias, and a function whose name is a live alias is a parse error that stops the rest of the file. For a function defined inside an `if` block the `unalias` goes before the block, because the shell parses the whole block before it runs any of it (`clean` and `mirror`), and it must not remove an alias that a later block defines (the Arch `mirror`).
- `tests/test_command_help.sh` enforces both rules without a list of its own. It takes every script, function, and alias from `commands --list` in each variant (plain, Ubuntu, Arch, Manjaro, Ubuntu on Windows, macOS) under Bash and Zsh, and runs `NAME -h` and `NAME --help` in a clean `env -i` shell, in a throwaway HOME and working directory, whose PATH holds a few harmless tools and tripwire stand-ins for `git`, `sudo`, `ssh`, `rclone`, `apt` and the like. A command fails when it exits non-zero, writes to stderr, prints no `Usage` line that names it, starts a tripwire, or changes a file, and the message names what it tried to start. It judges aliases as above (git aliases against a scratch repository with real `git`) and sources `aliases` over live aliases of the old names to check each `unalias`. A new command needs no entry: it fails until it answers `-h`.
- Validate catalog changes with `shellcheck .config/zsh/aliases .config/zsh/functions`, then source both files and run `commands` under Bash and Zsh, then run `bash tests/test_commands.sh` and `bash tests/test_command_help.sh`.
